## 0. 一页看懂

**做什么**：用 esbuild 把 22 个 TS 模块（203 KB）打成一个压缩后的 `dist/index.js`（83 KB），提交进仓库；pi 从此只加载这一个文件。

| | 现在 | 改完后 |
|---|---|---|
| pi 加载什么 | `index.ts` + 21 个模块，每次启动现场转译 | `dist/index.js` 一个文件，原生加载 |
| 体积 | 203 KB / gzip 54 KB | 83 KB / gzip 29 KB |
| 运行时依赖 | 0 | 0（并加门禁，保证永远是 0） |

**六条铁律**（整个方案就是围绕这六条设计的）：

| # | 铁律 | 谁来保证 |
|---|---|---|
| 1 | `dist/index.js` 必须提交进 git | 构建脚本 + 测试（忘了就红） |
| 2 | 产物里不允许 import 第三方包（要内联，不许外置） | 构建期扫描 + 测试 |
| 3 | 内联进产物的第三方包必须登记白名单 | 构建期 metafile 比对 + 测试 |
| 4 | 任何人重打，字节必须一模一样 | 打包器精确锁版 + 新鲜度测试 |
| 5 | `dependencies` 永远为空（pi 安装时什么都不装） | 测试 + 发布前校验 |
| 6 | 开发依赖用 lock 锁住并提交（现在 lock 被忽略了，要修） | `.gitignore` 改动 + 统一 `npm ci` |

## 1. 背景

需求就一句话：**打包出单文件、零依赖的 JS**。两个目的：

1. **杜绝产物层面的供应链攻击面**：产物只要还依赖外部包（import / node_modules），版本就控制不住、审不过来；全部内联 + 提交进 git 后，加载的就是审过的那份字节，不再随安装/更新漂移；
2. **精简代码、提升性能**：现在 pi 每次启动都要经 jiti（pi 内置的运行时 TS 加载器，现场把 TS 剥成 JS，非 JIT 编译）转译 22 个 TS 模块（203 KB）；改成 1 个压缩后的 JS（83 KB）后原生加载、零转译。

补充一点决定性约束：本扩展用 `pi install git:...@<分支>` 安装，所以产物必须提交进仓库（见 2.3）。

## 2. 设计决策

每条按"结论 → 为什么 → 代价"写。

### 2.1 打包器用 esbuild（不用 rollup）

- **为什么**：本仓库 22 个模块全部要用（DCE 后一个没少），没有可 tree-shake 的东西；只要 ESM 一种输出；没有 CSS/资源。esbuild 原生处理 TS，rollup 还要额外装 `@rollup/plugin-typescript` + `typescript`。esbuild ~70 ms 一次构建，新鲜度测试每次 `npm test` 都要跑构建。对"单文件"目标 rollup 反而有坑：动态 `import()` 默认拆出额外 chunk，必须额外配置；esbuild 单输出自动内联。抖动能力两者实测打平（附录 A.4）。
- **什么时候换 rollup**：将来内联大体积 ESM 依赖树时，rollup 的跨模块消除更省体积。构建逻辑只在 `scripts/build.js` 一个文件里，届时只改那里。

### 2.2 压缩档位：全量 minify + prompt 内联

- **结论**：`minify: true`（不用 `keepNames`）+ `legalComments: "none"` + 两个 prompt 文本 `?raw` 内联 → 83,197 B / gzip 28,898 B，dist 下只有一个文件。
- **为什么内联 prompt**：现在运行时 `readFileSync` 读 txt，路径靠 `import.meta.url` 推算。内联后删掉整段"文件读取 + 缓存 + 路径"逻辑（产物里 `import.meta.url`、`fileURLToPath` 都是 0 次），dist 真单文件，也消灭"txt 漏提交 → 分类器报错"。两端都支持：esbuild 配 `loader: {".txt":"text"}`；vitest（vite）原生支持 `?raw`。txt 仍是仓库里的唯一真源，只是构建时注入。
- **三件不做的事**（是真实风险，不是洁癖）：
  1. 不混淆属性名：状态会写进会话与配置文件，键名变了跨版本读不出来；且实测一分体积不省；
  2. 不 `drop:["console"]`：`console.warn` 是"拒绝注册不安全快捷键"等场景的唯一提示；
  3. 不声明 `"sideEffects": false`：现在没有纯副作用 import，声明了不省体积，将来却会静默丢掉 `import "./foo.ts"` 这类注册代码。
- **代价**：minify 后报错栈没有函数名。对策：`node scripts/build.js --no-minify` 本地打可读版本（不提交）；源码永远在仓库。

### 2.3 `dist/` 必须提交进 git（不能照抄 pi-web-access 的 gitignore dist）

- **为什么**：我们是 git 源安装。pi 对 git 源（已读 pi 1.0.0 源码 + 本地端到端模拟，附录 A.3/B）：
  - 安装 = `git clone` + `git checkout <分支>` + `npm install --omit=dev --legacy-peer-deps`——**不跑任何构建**，devDependencies 也装不上（esbuild 装不到）；
  - 更新 = `git fetch` + `git reset --hard` + **`git clean -fdx`**（未跟踪文件全删）+ `npm install`。
  - 结论：没提交进 git 的文件在安装目录里不存在；构建永远不会发生在安装目录。
- **反面案例（实测）**：manifest 指向 `./dist/index.js` 而 dist 未提交时，pi **不报任何错**，扩展直接不加载（只有恰好用 `--permission-mode` 这类本扩展注册的 flag 才会看到 `Unknown option`）。表现是"扩展莫名全失效"。
- **代价**：仓库多一个 83 KB 生成文件。`.gitattributes` 标 `linguist-generated` 折叠 diff；AGENTS.md 写明"改源码必须 `npm run build` 并提交 dist"，新鲜度测试兜底。

### 2.4 产物自包含：第三方包一律内联，白名单登记

- **结论**：external 只留 pi 宿主包（`peerDependencies` + `@earendil-works/*`），其余一律内联。
- **为什么**：这样产物不依赖任何运行时外部解析——**审核面收敛成一个文件**，审过的版本被 commit 冻结后不会再变。带 import 的产物做不到：每次安装/更新都重新解析 node_modules（可能漂移、可能有 `postinstall` 执行代码），审的是源码、跑的却是未经审阅的字节。
- **配套门禁**：
  1. 扫描产物 import：只允许 `node:*` / peer / `@earendil-works/*`（当前实测恰好 8 个说明符，全部合规）；
  2. `metafile` 比对：打进产物的第三方包必须与 `build.js` 顶部 `INLINED_THIRD_PARTY` 清单**完全一致**（当前清单为空）——多一个就构建失败，必须显式登记（包名 / 精确版本 / 体积 / 许可）。只扫 import 不够，必须配这条：第三方包被内联后不会留下 import 语句；
  3. 体积预算：原始 > 90 KB 或 gzip > 32 KB 构建失败（防止大库被悄悄打进 bundle）。
- **宿主包为什么必须外置**：pi 用 jiti（运行时 TS 加载器，非 JIT 编译）的虚拟模块提供 `@earendil-works/*` / `typebox`，官方文档明确禁止 bundle（会产生重复类 / 注册表，pi 还会报警告）。
- **引入第三方包的顺序**（价目表附录 A.5）：`node:` 内置 → 自己写 → 内联 + 登记。内联 `unpdf` 一个包就是 1.6 MB（本扩展的 20 倍），大包默认不引。

### 2.5 字节固定

- **结论**：`"esbuild": "0.28.2"` 精确锁版（不带 `^`）+ `dist.test.ts` 新鲜度比对（重打到临时目录，与提交的 dist 字节一致）。
- **为什么**：产物字节与打包器版本挂钩。实测 0.21.5 与 0.28.2 同输入输出字节相同，但不能指望未来一直如此；锁版 + 测试 = 任何人任何时候重打都得到同一份文件。升级打包器必须重跑构建并提交新 dist（预期的显式动作）。
- 由此得到"审核一次 = 长期稳定"：pi 更新取回的是 `git reset --hard` 的字节，npm / node_modules 都改不了它；两次 commit 之间的 dist diff 就是实际会跑的代码变化。

### 2.6 源码侧依赖治理（可以引 npm 包，但要锁得住）

- **现状问题**：`package-lock.json` 在 `.gitignore` 第 2 行，开发依赖树（本机 351 条目 / 208 个顶层包）完全没有版本管理。
- **结论**：
  - lock 从 `.gitignore` 移除并提交（锁住确切版本 + integrity 哈希，npm 安装时校验 tarball 完整性）；
  - 开发统一 `npm ci`；加/升包用 `npm install <pkg>@<精确版本>` 然后提交 lock diff——**lock 的 diff 就是依赖审计面**；
  - 要内联的第三方包放 `devDependencies`（它们是构建期输入），`dependencies` 永远为空；
  - 可选加固：仓库 `.npmrc` 写 `ignore-scripts=true`（注意 esbuild 靠 optionalDependencies 平台包，别用 `--omit=optional`）；定期 `npm audit signatures` 查 provenance。
- **诚实边界**：这些门禁挡得住"第三方代码悄悄进产物 / 运行时"，挡不住"构建工具链本身被攻陷"（那需要 CI 固定环境 + 签名）。

## 5. 风险与回滚

| 风险 | 对策 |
|---|---|
| dist 没提交 → 扩展静默不加载（最难排查） | 存在性断言 + 新鲜度测试；AGENTS.md 写明；提交前跑 `npm test` |

## 附录 B：pi 1.0.0 对包的处理（源码证据，`dist/core/package-manager.js`）

| 阶段 | 动作 |
|---|---|
| git 源安装 | `installGit()`：`git clone` → `git checkout <ref>` → `npm install --omit=dev --legacy-peer-deps` |
| git 源更新 | `updateGit()` → `ensureGitRef()`：`git fetch origin <分支>` → `git reset --hard <commit>` → `git clean -fdx` → `npm install --omit=dev --legacy-peer-deps` |
| 加载 | 读 `pi.extensions` → `collectFilesFromPaths()`：`if (!existsSync(p)) continue`（路径不存在 = 静默跳过） |
| npm 源安装 | 装进共享根 `~/.pi/agent/npm/`（所有 npm 插件共用一棵树 + 一个 lock） |
| 加载 TS 扩展 | jiti（运行时 TS 加载器，非 JIT 编译；Babel 系剥类型）逐模块转译（`moduleCache: false`，无磁盘缓存） |

另外两点安全事实：pi 的 npm 调用**不传 `--ignore-scripts`**（依赖的 `postinstall` 会执行；对比：pi 官方文档安装自家 CLI 用的是 `npm install -g --ignore-scripts`）；可选加固是 pi 设置 `npmCommand: ["npm","--ignore-scripts"]`。
