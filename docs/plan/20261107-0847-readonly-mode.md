# 只读（咨询）模式：给权限插件增加第五个模式

> 状态：**已实现**（2026-11-08 编码完成；396 个测试全绿，`dist/index.js` 已重建，待实机验收与提交）
> 日期：2026-11-07
> 计划分支：`feat/readonly-mode`（自 `dsh-78b2c2c9-3206` 最新提交 `1433f5e` 切出；该提交含本计划文档）

## 0. 一页看懂

**做什么**：新增第五个权限模式「只读」（`readonly`，显示名 `Read Only`，命令 `/readonly`）。它只允许读取与只读命令，**不建计划、不写计划文件、不进入执行流程**，模型把分析结论直接写在对话里。

**为什么**：现有 plan 模式虽然也是只读，但它绑定了整套计划流水线——建 `plan.md`、抽编号步骤、结束时弹「执行 / 留在计划 / refine」、执行后切 auto 并用 `[DONE:n]` 跟踪。做纯咨询（"这个软件有哪些功能、怎么用、有什么安全隐患"）时，这些机制会持续把模型的注意力拉向"先出计划、再实现"，而用户要的只是分析结论。

| 场景 | 现状（plan 模式） | 改完后（只读模式） |
| --- | --- | --- |
| 纯咨询提问 | 建 `plan.md`、催"出编号计划"、结束时弹执行/refine | 只回答：不建文件、不弹计划框、不催执行 |
| 模型想写代码 | 源码写不进去，但全程围绕"计划—执行"打转 | 写入工具根本不在工具集里，门禁再兜底拒绝 |
| 只读命令 | 放行 | 放行（沿用同一份只读白名单） |
| 配置里的 allow 规则 | 规则先于模式判定，可放行写入 | 只读是硬上限，allow 规则不能放宽 |
| 切模式 | — | 循环变为 `readonly → ask → plan → auto → bypass` |

**关键铁律**

1. 只读是**硬上限**：任何配置规则都不能让写入通过；deny 规则仍然生效。
2. 只读模式**不产生任何计划副作用**：不建、不读、不写计划文件，不弹计划批准，不自动切模式。
3. 只读是**工具层**保证，不是内核沙箱（pi 没有内置沙箱）——文档必须如实说明边界。
4. 不动 ask / plan / auto / bypass 的既有行为；不新增运行时依赖；模式切换不碰模型与思考强度。

## 1. 背景（已核实）

### 1.1 DSH 的「仅可查看」是什么

- Web GUI 里的「仅可查看」是 DSH 的权限预设 `read-only`：它把两个独立开关捆在一起——文件沙箱 `read-only` + 审批策略 `ask`（见 DSH 基础组合配置 `packages/bundle/base/cordis.patch.yml` 的预设表）。
- 强制执行发生在**文件系统层**：`read-only` 模式下沙箱拒绝一切写入（POSIX 后端只额外放行 shell 必需的 `/dev/null`）。模型每轮会看到一段策略说明（`Current DSH file policy: read-only…`）；真被拒绝时，工具返回 `[sandbox: file access denied under <mode> mode]` 并附同回合的升级提示——可以申请一次更宽的权限，由审批弹窗让用户确认。
- 关键点：DSH 的「仅可查看」**只定义文件效果，不定义"要不要做计划"**；DSH 的计划能力是另一个独立子系统。也就是说，用户想要的效果 = DSH 的只读权限语义 + **不进入计划流水线**。

### 1.2 pi 与本插件的现实约束

- **pi 没有内置沙箱**（pi 自己的安全文档明确说明）：工具以 pi 进程的权限读写文件、执行命令。扩展只能在工具调用前后拦截，或把工具从模型可见的工具集里移除。因此本插件的"只读"只能是**工具调用层 + 工具集层**的保证，无法阻止未被拦住的扩展工具或白名单漏网命令写文件。
- pi 确实提供了启动期的 `--tools` 白名单（例如只给 read/grep/find/ls），但那是**进程启动时**的静态配置：会话内不能切换、不覆盖 bash 的只读命令、也不参与本插件的模式体系。本需求要的是会话内可切换的版本。
- pi 内置工具固定为 8 个：读、写、编辑、bash、powershell、grep、find、ls；其余都是扩展工具。扩展 API 不提供"这个工具是否只读"的元数据（工具信息里只有名称、描述、参数、提示、来源），所以**未知工具只能由插件自己分类或按配置判断**。
- 工具带**来源信息**（`sourceInfo`：`source` / `path` / `scope` / `origin`），由 pi 在加载时盖章、插件无法伪造；`pi.getAllTools()` 可在运行时查询。这是"按插件放行"的依据：`npm:pi-web-access` 这类来源字符串直接对应 settings 里的包声明。
- **powershell 完全没有适配**（源码与产物里 `powershell` 零命中）：
  - 所有 shell 判断都只认 `bash`，`powershell` 进不了任何 shell 分支。
  - ask 模式与 plan 模式都会落到门禁末尾的默认放行——**不弹窗、不拦截**。也就是说 plan 模式在 Windows 上（按 pi 文档启用 powershell 时）"只读"并不成立：powershell 可以随意写文件。
  - auto 模式会把它当作"未知工具"送进 tier-3（有 UI 弹窗、无 UI fail-closed），但拿不到命令内容做风险判断，只是"拦一下"。
  - 权限规则也表达不了：规则映射表里没有 powershell，写 `PowerShell(...)` 永远匹配不上。
  - 环境事实：pi 默认激活的工具是 read/bash/edit/write，`powershell` 是 Windows 上的**可选**内置工具，需在 settings 的 `defaultTools` 里显式启用（pi 的 Windows 文档如此建议）。所以这个洞只在"Windows + 启用了 powershell"时暴露，而那正是 Windows 用户的推荐配置。
  - 本期决定（2026-11-07）：**保持原状，不做任何 powershell 适配**；缺陷已记录为 [docs/issues/20261107-powershell-not-gated.md](../issues/20261107-powershell-not-gated.md)。只读模式下它按"未知工具默认拒绝"处理，不写 powershell 专用逻辑。
- **门禁顺序是：bypass 早退 → 配置规则求值 → 模式分支**。所以只读判定如果放在模式分支里，一条针对编辑/写入的 allow 规则会先返回"允许"，从而绕过只读。只读必须**前置于规则求值**，或让规则求值感知当前模式。
- 现有 plan 模式已经是"只读 + 只能写 plan.md"，但：
  - 进入时创建 `.pi/projects/<id>/plan.md`；
  - 每轮注入"探索 → 出编号计划 → 告诉用户计划已就绪"的提示；
  - 回合结束时抽取 `Plan:` 编号、弹计划批准对话框；
  - 选择执行后切到 auto，并用 `[DONE:n]` 跟踪进度。
  这套机制正是纯咨询时不需要、且会分散注意力的部分。
- 计划模式其实**没有**真的把编辑/写入工具从模型可见工具集里移除（当前"禁用工具集合"是空的），与提示参考文档里"已移除"的描述不一致；真正拦住写入的是工具调用门禁。这一点对只读模式有直接影响：只读应当**真的把写入工具从工具集移除**（模型看不到，也就不会反复尝试），门禁再兜底。
- 现有只读命令判定：把复合命令按 `;` `&&` `||` `|` 与换行拆段，每段都必须命中只读允许表，且不能命中破坏性规则（`>` / `>>` 重定向、`rm/cp/mv/mkdir/touch/chmod`、`find -exec/-delete`、包管理器安装、git 写操作、sudo 等）。plan 模式与 ask/auto 都复用它；只读模式应直接复用，避免出现两套标准。
- 模式相关的既有机制：循环顺序硬编码、模式随会话持久化并在恢复时校验、`--permission-mode` 启动旗标、`/mode` 选择列表、底部状态栏、子代理通过环境变量继承父模式。新增模式必须逐一覆盖，否则会出现"父会话只读、子代理却能写"这类漏洞。

## 2. 需求目标（验收标准）

### A. 模式与入口

1. 新增第五个模式：键名 `readonly`，显示名 `Read Only`；底部状态栏有独立图标与配色（与 ask/plan/auto/bypass 可区分）。
2. 可用 `/readonly` 进入；`/mode` 列表可见并可选；`--permission-mode readonly` 可作启动模式；Shift+Tab 循环可到达。
3. 循环顺序为 `readonly → ask → plan → auto → bypass → readonly`（见决策点 D1）。
4. 模式随会话持久化、恢复；恢复时非法值仍按现有规则忽略。

### B. 只读保证

5. 写入类工具（编辑、写入）在只读模式下**从模型可见工具集中移除**；即使被其他扩展重新加回，门禁也一律拒绝（双保险）。
6. 配置中的 **allow 规则不能放宽只读**：写类工具、非只读命令都不得因 allow 规则通过；**deny 规则仍然生效**。
7. bash 仅放行只读命令（复用现有白名单与破坏性判定）；被拒时给出可操作的理由——说明当前是只读模式、需要写入请切换模式，而不是静默失败。
8. `powershell` 在只读模式下不放行；本期不为它做专门适配，它按"未知工具默认拒绝"处理（依赖 D2）。
9. 未知/扩展工具默认**不放行**；本期只提供一种放行方式，且代码里不内置任何插件名或工具名：
   - 内置只读工具（read / grep / find / ls）始终放行；
   - `~/.pi/agent/permission-modes.json` 的 `readonly.allowPlugins` 按**插件**放行，默认空：填包名（如 `pi-web-access`）或完整来源（如 `npm:pi-web-access`），命中后该插件注册的全部工具放行——覆盖工具改名、插件升级、动态激活（如 `web_enable`）；
   - 匹配为**精确匹配**（大小写不敏感），`npm:` 前缀、版本后缀、git 分支后缀会先归一化；不做子串与通配，避免 `pi` 之类的短名误豁免其它插件；
   - 未列出的插件工具一律拒绝；拒绝理由带来源与配置提示；
   - 本期不提供按工具名放行与通配，后续需要再加。
10. 读类工具（读/检索/列目录）不弹窗，包括工作目录之外——与 plan 模式一致，分析场景不应被打断；需要更严时用户用 deny 规则（见决策点 D3）。

### C. 无计划副作用

11. 进入只读模式**不创建**计划文件；整个会话不读、不写、不展示计划文件内容。
12. 只读模式下**不弹**计划批准对话框、不做步骤抽取、不做 `[DONE:n]` 跟踪、不自动切换模式、不注入"先出计划"的指令。
13. 模型可见的模式提示保持简短（不超过 5 行）且每轮稳定；核心语义是：这是分析/咨询模式，结论写在对话里；除非用户明确要求，不要产出实施计划或实现方案；判断需要改动时，用一两句话说明建议后停下；不要以"要不要我帮你实现"收尾。

### D. 兼容与安全

14. 工具集按名字增减，不做整表快照恢复：进入只读时移除写入类工具，离开时按名字加回；与同样会动态管理工具集的扩展（如 pi-web-access 用 `web_enable` 调 `setActiveTools` 激活联网工具）共存，互不覆盖、互不丢失。
15. 无 UI 环境（`-p` / JSON / RPC）行为一致：该拒的拒，绝不因为无法弹窗而放行；同时因为只读模式本就不该弹窗，它在无人值守的分析任务里应能全程无阻塞运行。
16. 子代理继承：父会话只读时，子代理也必须是只读（否则"派个子代理去写"就是绕过路径）。
17. 其余四个模式的判定结果与副作用零变化。

## 3. 验证

- **单元测试**：只读命令判定的回归（沿用现有白名单，不新增第二套标准）；工具分类（内置写入类 / 内置只读类 / 未知类）；模式提示的稳定性与长度。
- **集成测试**（沿用现有 fake-pi 模式）：
  - 写 / 编辑被拒，且拒绝理由可操作；
  - 针对写与写命令的 allow 规则不能放行；deny 规则仍然拦截读取；
  - bash 只读命令放行、写命令拒绝；
  - powershell 不放行（按未知工具默认拒绝；不做 powershell 专门适配）；
  - 未知工具默认拒绝，配置放行后通过；
  - 插件放行：配置 `pi-web-access` 后，`web_enable` / `web_search` / `fetch_content` / `get_search_content` 可调用，且 `web_enable` 激活出的工具不会被下一轮工具集整理移除；
  - 插件放行的匹配：包名、完整来源（`npm:pi-web-access`）、带版本或分支后缀的来源都能命中；`pi` 这类短名**不会**命中 `pi-web-access`；
  - 未列出的插件工具一律拒绝，拒绝理由含来源与配置提示；拿不到来源信息时拒绝（fail-closed）；
  - edit / write / powershell 即使插件命中也不放行；
  - 进入只读不创建计划文件、回合结束不弹计划对话框；
  - readonly ↔ plan ↔ ask 切换后工具集正确恢复；
  - `/readonly`、`/mode` 列表、启动旗标、会话恢复、子代理继承。
- `npm test` 全绿（Windows 基线上已知的无关失败需对照基线说明）。
- `npm run build` 重建 `dist/index.js` 并提交；产物新鲜度门禁与体积预算通过（当前产物 86,807 B raw、gzip 约 30.0 KB；预算 92,160 B / 32,768 B，raw 余量约 5.2 KB、gzip 余量约 2.7 KB，需控制增量）。
- **实机验收**（关键）：
  1. `/readonly` 后问"分析这个仓库有哪些功能、怎么用、有什么安全隐患" → 模型只给分析，不建 `plan.md`、不弹计划框、不主动写代码；
  2. 故意要求"帮我改一下某文件" → 调用被拒、理由正确；用户切到 `/ask` 后写入恢复；
  3. 观察底部状态栏与 Shift+Tab 循环；
  4. 开一个子代理，确认它同样不能写。

## 5. 明确不做的事

- 不改默认模式：新会话仍从 ask 开始；需要默认只读时用 `--permission-mode readonly` 启动。
- 不做系统调用级沙箱，不引入容器 / VM / 内核级隔离。
- 不改 pi 本体，不 patch pi 的工具实现。
- 不改 ask / plan / auto / bypass 的既有判定与副作用（含计划流水线）。
- 不做任何 powershell 适配（命令判定、规则映射、现有模式的门禁）；该缺陷已记录为已知问题：`docs/issues/20261107-powershell-not-gated.md`。
- 不做通用的"按模式过滤工具"框架（那是另一条独立需求）；本期只做只读模式需要的工具集控制。
- 不拦截用户自己用 `!` 触发的命令（那是用户本人的操作，不是模型的工具调用；只读模式约束的是模型）。
- 不新增第三方运行时依赖；不自动提交、不推送、不发版（WORKFLOW §7）。

## 6. 风险与备注

1. **能力边界必须讲清楚**：pi 无沙箱，只读是工具层保证。插件级放行是"信任声明"而不是"只读验证"——你放行的插件如果自带写工具，只读挡不住；未被放行的插件工具一律拒绝。README 要写明这是"防误写"，不是"防恶意"。
2. **放行策略的取舍**：本期只做"插件级放行 + 精确匹配 + 默认空"，代码不内置任何第三方工具名或插件名。代价是只读模式下除配置过的插件（目前只有 pi-web-access）外，其它扩展工具都会被拒——这是 2026-11-07 的明确取舍，不是缺陷。
3. **门禁顺序**：只读判定必须前置于配置规则求值，否则 allow 规则会绕过。这是实现时最容易踩的坑，测试要专门覆盖。
4. **powershell 本期不修**：现有 plan / ask 模式的 powershell 缺口比"只读模式要拒绝它"更大——plan 模式的只读保证在 Windows + 启用 powershell 时本来就是破的。2026-11-07 决定本期保持原状，缺陷记录在 [docs/issues/20261107-powershell-not-gated.md](../issues/20261107-powershell-not-gated.md)；只读模式靠"未知工具默认拒绝"自然挡住它（依赖 D2）。给 powershell 做只读命令白名单是另一个量级的活（`Remove-Item` / `Set-Content` / `Out-File` / 管道重定向……），不在本期。
5. **工具集记账与第三方扩展的冲突**：现有实现用一个变量记住进入 plan 前的工具集，离开时整表恢复。pi-web-access 这类扩展会自己调 `setActiveTools`（`web_enable` 动态激活、`session_start` 重写工具集），整表恢复会把对方刚加的工具冲掉、或把已移除的写入工具带回来。只读模式必须按名字增减，并有与"动态激活类扩展"共存的测试。
6. **循环顺序变更**：把只读插到队首后，唯一变化的跳转是"bypass → 下一个"。若更希望"只读排在最后"，改动很小（D1）。
7. **提示词注意力**：只读模式的价值一半在"不写"，一半在"不想着写"。提示过长会反噬（占注意力、诱导模型复述规则）。要求 ≤5 行、稳定不变。
8. **体积预算**：raw 余量约 5.2 KB，新增模式 + 提示 + 分类逻辑预计 1–2 KB，仍在预算内；若逼近上限，按构建脚本规则小幅上调并在 CHANGELOG 记录理由。
9. **AGENTS.md 冲突**：其"不变式"写着四模式循环硬编码。新增第五模式后该句过时。按 WORKFLOW §6 默认不改，需用户决定是否授权同步这一行。
10. **版本**：新功能建议 minor（3.2.0），但发版由用户决定。
11. **联网工具不是纯只读**：放行 pi-web-access 后，`fetch_content` 会把 GitHub 仓库 clone 到 `/tmp/pi-github-repos`（用完清理）、把抓取结果缓存到 `~/.pi/agent/web-search-cache`、PDF / 视频帧提取写临时文件。这些都不写工作区，README 的边界说明要写清"只读 = 不修改项目文件"，而不是"不落盘"。
12. **联网内容的注入面**：抓回来的网页可能带提示注入。只读模式下模型写不了文件，破坏面被压到"回答被污染"，比 auto / bypass 小；这反而让只读模式适合读不可信来源。

## 7. 决策点与结论（已确认）

> **审阅结论（2026-11-07）**：D1–D6 已确认。D5：只读模式与 plan 模式保持一致，只移除编辑/写入能力，不加 `readonly.bash: off`。D6：放行只做插件级精确匹配、默认空，代码不耦合任何插件名或工具名。

| 编号 | 问题 | 推荐 | 备选 |
| --- | --- | --- | --- |
| D1 | 只读在循环中的位置 | 队首：`readonly → ask → plan → auto → bypass`（权限从紧到松；只改变 bypass→X 一跳） | 队尾：`ask → plan → auto → bypass → readonly` |
| D2 | 未知工具默认策略 | 默认拒绝 + 可配置放行；拒绝理由给出放行方法 | 默认放行（弱保证） |
